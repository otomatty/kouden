# 01. 決定事項 (ADR)

各決定は「決定 / 理由 / 影響」で記録する。変更する場合は新しい ADR を追加し、古いものに「置換済み」と書く（削除しない）。

---

## プロダクト

### ADR-P01 香典帳 1 冊 = 故人 1 人。中に「行事」を持つ
- **決定**: 香典帳は故人単位。通夜・告別式・四十九日・一周忌などは香典帳内の「行事 (event)」として持つ。
- **理由**: 同じ差出人が複数の行事で香典を出すケースを名寄せでき、香典返しを人単位でまとめられる。
- **影響**: Durable Object の単位 = 香典帳。行事をまたぐ集計は DO 内で完結する。
- **更新（2026-10-22）**: 香典帳を作るときに用意する行事は「葬儀」1 つにする（通夜と告別式の香典をまとめる）。分けたい人や四十九日などの法要は、設定で行事を足す。行事が 1 つなら登録画面で行事を選ばせない。行事の種類は今のまま（`funeral` の表示名だけを「葬儀・告別式」にする）。分類は [08](./08-gift-entry-ux.md) §7.1。

### ADR-P02 香典・供物・供花・弔電を「いただきもの」台帳に統合
- **決定**: 現行の `kouden_entries` / `offerings` / `telegrams` を 1 つの `gifts` テーブルに統合し、`kind` で区別する。
- **理由**: 1 人が香典と供花を両方出す場合の扱い、香典返しの合計計算、一覧・検索・出力が一元化される。現行の `has_offering` のような非正規化フラグが不要になる。

### ADR-P03 差出人は香典帳内で名寄せする
- **決定**: `persons`（差出人）を香典帳ごとに持ち、いただきものは差出人に紐づく。連名は `gift_contributors` で複数人に紐づける。
- **理由**: 香典返しは「人」に対して行うため。香典帳をまたぐ住所録は作らない（DO をまたぐ設計を避ける）。

### ADR-P04 受付番号を行事ごとに自動採番
- **決定**: いただきもの登録時に、行事ごとの通し番号（1, 2, 3…）を DO が採番する。移行データは番号なし。
- **理由**: 香典袋とデータの照合に使う。DO は単一スレッドで処理するため、同時入力でも番号が重複しない。
- **更新（2026-10-22）**: 受付機能の廃止（ADR-P18）にあわせて、呼び名を「受付番号」から「番号」にする。登録後の画面で番号を大きく出し、家族が香典袋に書いて記録との照合・管理に使う。いただきものの一覧は番号でも探せる（「12」「No.12」）。採番の仕組みとデータ（`events.next_receipt_no`・`gifts.receipt_no`）は変えない。

### ADR-P05 変更履歴をユーザーに見せる
- **決定**: DO 内に追記専用の変更ログ (`change_log`) を持ち、記録ごとの履歴画面で表示する。
- **理由**: 金額の入力ミスの追跡、家族間の確認。同じログをリアルタイム通知の連番にも使う（ADR-T06）。

### ADR-P06 権限は固定 3 ロール
- **決定**: `owner`（全操作・課金・譲渡・削除）/ `editor`（記録の入力・編集）/ `viewer`（閲覧のみ）。現行のカスタムロールは廃止。
- **理由**: 権限チェックと UI が単純になる。現行のカスタムロールは移行時に機械的に 3 ロールへ写像する（[05](./05-migration-plan.md)）。

### ADR-P07 招待は招待リンクのみ
- **決定**: 有効期限・使用回数上限・付与ロール付きの招待リンク（URL / QR コード）。メールでの招待は行わない。
- **理由**: LINE 等で共有する実際の利用形態に合う。メール送信が不要。

### ADR-P08 オーナーの譲渡
- **決定**: 現オーナーが既存メンバーを指名 → 相手が承諾 → 入れ替え。旧オーナーは `editor` になる。購入状態は香典帳に付いたまま。
- **理由**: 喪主の交代、親族への引き継ぎ。アカウント削除時の受け皿にもなる（ADR-P12）。

### ADR-P09 香典返し機能の範囲
- **決定**: 返礼品カタログ、金額帯ルールによる自動提案、対応状況（未対応 / 手配済み / 発送済み / 当日返し済み / 不要）の管理、法要日程からのリマインド（メール）。

### ADR-P10 課金: 香典帳ごとの買い切り、無料版は件数上限
- **決定**:
  - 無料: 1 冊あたり **いただきもの 30 件まで**。機能制限はなし。
  - 有料: **1 冊 ¥2,980（税込）買い切り**、件数無制限。その冊のすべての行事を含む。
  - 移行した既存の香典帳はすべて有料扱いにする。
- **理由**: 家族葬（20〜30 件）は無料で完結し、一般葬（50〜150 件）で購入を促す。現行ベーシックと同額で価格の連続性を保つ。プランを 1 段階にすると判定と料金ページが単純になる。
- **件数の定義**: 論理削除されていない `gifts` の行数。

### ADR-P11 出力は印刷用ページと Excel
- **決定**: 印刷用 CSS を当てた HTML ページ（ブラウザから印刷 / PDF 保存）と `.xlsx`。サーバー側での PDF 生成は行わない。

### ADR-P12 データはユーザーが削除するまで保持
- **決定**: 自動削除はしない。アカウント削除時は、オーナーである香典帳ごとに「譲渡」か「削除」を必ず選ばせる。メンバーとしての参加は解除する。

### ADR-P13 オフライン対応はしない
- **決定**: オフライン時は警告バナーを出し、送信ボタンを無効化する。Service Worker による書き込みキューは作らない。

### ADR-P14 公開サイトは最小限
- **決定**: LP・料金・FAQ・利用規約・プライバシーポリシーのみ。マイルストーン・キャンペーン・アンケート・ヒアリング申込は廃止。

### ADR-P15 運営者機能はユーザー / 香典帳の検索・閲覧と統計のみ
- **決定**: 問い合わせチケット、お知らせ配信は作らない。問い合わせはメール窓口で受ける。

### ADR-P16 対象端末はスマホとデスクトップの両方
- **決定**: 受付入力画面はスマホ優先（大きな受付番号表示・片手操作）。一覧・集計・香典返し・印刷はデスクトップ優先（キーボードでの連続入力）。
- **一部置換済み（2026-10-22）**: 受付入力画面は廃止した（ADR-P18）。いただきものの登録画面は、スマホとデスクトップの両方で使う 1 列のフォームにする。

### ADR-P17 旧メールログインユーザーの自動紐づけは Gmail / Google Workspace のアドレスに限る
- **決定**: 旧アプリでメール OTP ログインしていたユーザーは、Google が持ち主を保証できるアドレスの場合だけ、初回の Google ログインで自動的に旧アカウントへ紐づける。対象は `@gmail.com` / `@googlemail.com`、または ID トークンの `hd`（Google Workspace のドメイン）がメールのドメインと一致する場合。それ以外は運営者が本人確認のうえ手動で紐づける。旧 Google ログインのユーザーは移行時に `sub` で紐づける（メールは使わない）。
- **理由**: `email_verified` は Google アカウント作成時に確認したことしか示さない。Gmail 以外のアドレスは後から別人に再割り当てされうるため、その新しい持ち主が旧ユーザーの香典帳（個人情報）にアクセスできてしまう。
- **代償**: 携帯キャリアやプロバイダのメールで登録していた人は、問い合わせが必要になる。切り替え前の告知で案内する。

### ADR-P18 受付機能を廃止する（2026-10-22）
- **決定**: 葬儀当日の受付でアプリに入力することを前提にした機能をなくす。対象は、受付画面（`/k/:id/reception`。行事の切り替え・大きな受付番号の表示・htmx による連続入力）、香典帳のメニューの「受付」、招待リンクから参加した編集者を受付画面へ送る導線、ペルソナ「受付の手伝い」。いただきものは「いただきもの」の画面から登録する（`/k/:id/gifts/new`）。
- **理由**: 設計の見直しで、受付の機能は不要と判断した。登録の主な場面は「葬儀の後に、家族が手元の香典袋・芳名帳を見ながら入力する」とし、その場面で簡単に登録できることを優先する（[08](./08-gift-entry-ux.md)）。
- **影響**:
  - 登録画面は通常のフォーム（POST → 同じ画面へリダイレクトし、登録した内容を上に表示して続けて入力できる）。08 の結論が出るまでの暫定で、項目は受付画面と同じ。
  - 受付番号の採番とデータは残す（ADR-P04）。DO・D1 のスキーマは変えない。
  - 招待リンクから参加した人は、ロールにかかわらず香典帳のトップに移る。

### ADR-P19 いただきものの一覧と入力は、PC は表・スマホはカード（2026-10-22）
- **決定**: [08](./08-gift-entry-ux.md) の案 C（表で入力）と案 D（写真から読み取る）を採る。表計算ソフト（Excel）のように表で連続して入力するのは PC（画面幅 768px 以上）だけの動きにする。スマホのいただきもの一覧は、1 件を 1 枚のカードにして表示する（番号・差出人・種別・金額）。
- **理由**: 葬儀の後に香典袋を見ながら入力する場面（ADR-P18）では、件数の多い PC の入力は表が速い。スマホの幅では表の横スクロールと細かいセルの操作が難しい。
- **影響**:
  - 一覧は同じ HTML に表とカードの両方を出し、CSS（Tailwind の `md`）で出し分ける。JS で端末を判定しない。
  - 写真の読み取りで送るデータの扱いは ADR-T16。

## 技術

### ADR-T01 実行基盤は Cloudflare Workers（Paid プラン）
- **決定**: Vercel / Supabase を廃止し、Workers・Durable Objects・D1・R2・Email Service・Cron Triggers で構成する。
- **理由**: DO と Email Sending が Paid プラン前提。単一ベンダーで完結する。

### ADR-T02 画面は Hono JSX（SSR）+ htmx + Tailwind CSS
- **決定**: React を使わない。サーバーで HTML を生成し、部分更新は htmx 2.x。スタイルは Tailwind CSS（ビルド済み CSS を静的配信）。
- **理由**: クライアント JS が数十 KB で済み、状態管理ライブラリが不要。ビルドが単純で保守しやすい。
- **却下した案**: HonoX（v0.1 系で 1.0 未到達のため）、Next.js on OpenNext（アダプタ依存のため）。
- **例外**: どうしてもクライアント状態が必要な部品が出た場合のみ `hono/jsx/dom` のアイランドを使う。

### ADR-T03 認証は Google OIDC を Hono で自前実装
- **決定**: Authorization Code + PKCE + state + nonce。メール OTP・パスワードは廃止。セッションは不透明トークンを Cookie に入れ、D1 にハッシュを保存する。
- **却下した案**: Cloudflare Access をエンドユーザー認証に使う案。Zero Trust はログインしたユーザー 1 人ごとにシートを消費し、無料枠 50 人を超えるとログインがブロックされる。一般向け有料サービスには不適。

### ADR-T04 運営者画面は別 Worker + Cloudflare Access
- **決定**: `admin.kouden.app` に `kouden-admin` Worker を置き、ホスト全体を Cloudflare Access（Google IdP、運営者のメールのみ許可）で保護する。Worker 側でも `Cf-Access-Jwt-Assertion` を検証する。
- **理由**: 本体 Worker に管理機能のコードを入れない。運営者は数名なので Zero Trust 無料枠に収まる。

### ADR-T05 データ配置: 香典帳ごとの Durable Object + D1
- **決定**:
  - **DO `KoudenLedger`（SQLite）**: 1 冊の中身すべて（行事・差出人・いただきもの・関係・香典返し・リマインド・変更ログ）。
  - **D1**: ユーザー、セッション、香典帳の目録、メンバーシップ、招待、譲渡、購入、統計用の要約、運営者の監査ログ。
- **理由**: ほぼすべての操作が 1 冊の中で完結する。DO の直列実行で採番・整合性・リアルタイム配信が自然に解ける。テナント分離が物理的になる。
- **代償**: 冊をまたぐ集計は D1 への要約投影で行う。DO のスキーマ移行はオブジェクトごとに遅延適用する仕組みが必要（[03 §4](./03-domain-model.md#4-do-スキーマの移行)）。

### ADR-T06 リアルタイム: 記録単位の同期 + 編集中表示
- **決定**: DO が WebSocket（Hibernation API）で「何が変わったか」だけを通知し、各端末は htmx で該当部分を取り直す。同時編集はバージョン番号で検出する。「○○さんが編集中」を表示する。
- **理由**: HTML をブロードキャストしないので、閲覧者・編集者で表示が違っても通常の権限チェックがそのまま効く。
- **却下した案**: CRDT による文字単位の同時編集（クライアントアプリが重くなり方針に反する）。

### ADR-T07 メールは Cloudflare Email Service
- **決定**: `send_email` binding で `noreply@kouden.app` から送る。`Mailer` インターフェースで抽象化する。
- **リスク**: Email Sending はベータ版。問題があれば Resend 実装に差し替える。

### ADR-T08 独自ドメインを Cloudflare Registrar で取得
- **決定**: アプリ `kouden.app`、運営者画面 `admin.kouden.app`（2026-10-19 取得）。ステージングは独自ドメインを使わず `workers.dev` に置く。
- **理由**: Email Sending は Cloudflare 上の自ドメインからしか送れない。Google ログインのブランド確認にもドメインが必要。

### ADR-T09 決済は Stripe Checkout（一回払い）
- **決定**: Checkout Session を作成し、Webhook（署名検証 + イベント ID で冪等化）で購入を確定する。

### ADR-T10 開発ツール
- **決定**: Bun（パッケージ管理・スクリプト）、`cf`（ADR-T15）、Oxlint、oxfmt、TypeScript 7、Vitest + `@cloudflare/vitest-plugin`、Playwright。
- **注意**: oxfmt は 1.0 未到達のため、バージョンを固定し、更新は差分を確認してから行う。
- **注意**: Vitest 5 のファイルシステムキャッシュ（`fsModuleCache`）は `@cloudflare/vitest-plugin` 1.4.0 と組み合わせると失敗するため無効にしている。

### ADR-T11 監視は Workers Logs / Observability のみ
- **決定**: 構造化 JSON ログ（requestId・userId・koudenId を付与）。外部監視サービスは使わない。

### ADR-T12 環境は本番 + ステージング
- **決定**: `cf` の mode（`development` / `staging` / `production`）で Worker 名・D1・R2 を分離する。DO の名前空間は Worker ごとに分かれるので、Worker 名を分ければ自動で分離される。ステージングはホスト全体を Cloudflare Access で保護する。

### ADR-T13 リポジトリは同一リポジトリで全面置き換え
- **決定**: 開発中は新実装を `v2/`（独立した Bun ワークスペース。中に `apps/` `packages/` `tools/`）に置き、旧実装（`src/` ほか）と同居させる。旧アプリは切り替えまで Vercel で動き続ける。切り替え後に `legacy-nextjs` タグを打ち、旧実装を削除して `v2/` の中身をリポジトリ直下へ移す。移行ツールも同じリポジトリに置く。
- **理由**: 旧実装の `package.json`・`tsconfig.json`・Biome がリポジトリ直下にあり、そこにワークスペースを足すと旧アプリのビルドに影響するため。旧実装側の `tsconfig.json` と `biome.json` では `v2` を対象外にしている。
- **更新（2026-10-21）**: 一般公開の後、`v2/` の中身をリポジトリ直下へ移した。旧実装は削除せず、参照用に `legacy/` へ移した（保守・CI・デプロイはしない。旧アプリ用の `test.yml`・`sync-to-oss.yml` は削除）。

### ADR-T14 切り替えはメンテナンス停止による一括移行
- **決定**: ステージングでリハーサルした後、告知した日時に旧アプリを停止して全データを移す。

### ADR-T15 CLI は `cf`（ベータ）+ Vite を使う
- **決定**: wrangler ではなく Cloudflare CLI `cf` を使う。設定は TypeScript の `cloudflare.config.ts`、ビルドは Vite（`@cloudflare/vite-plugin` 2.0 beta）。`cf` と Vite plugin はバージョンを固定する。
- **理由**: 設定が型付きで、binding の型が自動生成される。mode ごとに完全な設定を返すので、環境ごとの設定漏れが起きにくい。DO は `exports.durableObject({ storage: "sqlite" })` の宣言だけで済み、`migrations` の履歴管理が不要。
- **ベータ版ゆえの回避策**（M0 時点、`cf` 1.0.0-beta.14）:

  | 課題 | 回避策 |
  |---|---|
  | `cf` にライブログ（tail）がない | Workers Logs のダッシュボードを使う。必要時のみ `npx wrangler tail <Worker 名>` |
  | シークレットを 1 つだけ登録できない | デプロイ時に `cf deploy --secrets-file` で渡す（CI で実施） |
  | Vitest 連携が `cloudflare.config.ts` を読めない | `vitest.config.ts` に binding を宣言し、キーが一致するかを起動時に検査する |
  | `cf d1 migrations apply --local` が不安定（応答が返らないことがある） | ローカル D1 は Miniflare を直接使うスクリプト（`bun run db:migrate:local`）で適用する |
  | `cf d1 migrations apply` は ID しか受け付けず、既定でリモートに適用する | `bun run db:migrate -- --mode <mode>` が名前から ID を引いて適用する |
- **撤退条件**: 正式版までに重大な不具合が続く場合は、`cloudflare.config.ts` を `wrangler.jsonc` に書き直して wrangler に戻す（アプリのコードはそのまま使える）。

### ADR-T16 写真の読み取りに使う AI は、送ったデータを学習に使わないものに限る（2026-10-22）
- **決定**: 香典袋の中袋・芳名カードの写真から氏名・金額・住所を読み取るため（ADR-P19・案 D）、写真を外部の AI の API に送ってよい。ただし、送ったデータをモデルの学習に使わないことが規約・契約で約束されている API に限り、学習への利用を許す設定（オプトイン）は使わない。
- **理由**: 住所の手入力が登録でいちばん手間がかかる。一方、写真は差出人の個人情報なので、学習への利用は認めない。
- **影響**:
  - 送り先の候補は、Anthropic の Claude API（画像の入力と、JSON の形を決めた出力に対応）と Cloudflare Workers AI（同じベンダーで完結する）。採用の前に、最新の規約で「学習に使わない」ことと保持期間を確かめ、実物の香典袋で精度と費用を比べて決める。
  - 読み取った結果は下書きにして、人が確かめてから登録する（そのまま登録しない）。
  - 写真と読み取った結果をログに出さない。API キーはシークレットにする（コード・ログに書かない）。
  - プライバシーポリシーに、送り先と目的、学習に使われないことを書く。
  - 写真をアプリに保存するかは [08](./08-gift-entry-ux.md) §7 で決める。

### ADR-T17 郵便番号から住所を入れるデータは、日本郵便の公開データを Static Assets に置く（2026-10-22）
- **決定**: 日本郵便の「住所の郵便番号（1レコード1行、UTF-8形式）」を、郵便番号の先頭 3 桁ごとの JSON（`/postal/<3 桁>.json`）に変換して Static Assets に置く。画面は入力された郵便番号の先頭 3 桁のファイルだけを読み、都道府県・市区町村・町域を住所の欄に入れる（[08](./08-gift-entry-ux.md) 案 E）。データは Git に入れず、デプロイのたびに最新のものを取得して作る（`bun run postal -- --download`）。
- **理由**: 利用者が入れた郵便番号を外部の API に送らずに済む。D1 や Worker を通さず、CDN から配れる。日本郵便は郵便番号データの著作権を主張しておらず、自由に配布できる。
- **影響**: デプロイ時に日本郵便のサイトからデータを取れないと、デプロイが止まる（再実行する）。件数が 10 万件を下回るときは、形式が変わったとみなして止める。ローカル開発ではデータがなく、住所は入らない（`--input` で手元のファイルから作れる）。
