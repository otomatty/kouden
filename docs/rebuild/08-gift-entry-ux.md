# 08. いただきものの登録をかんたんにする

状態: **一部決定**（2026-10-22）。決まったことは §6 と ADR（P04・P18・P19・T16）に記録した。残っていることは §7。

受付機能の廃止（[ADR-P18](./01-decisions.md#adr-p18-受付機能を廃止する2026-10-22)）にあわせて、香典・供物・供花・弔電の登録をもっと簡単にする案をまとめる。今の登録画面（`/k/:id/gifts/new`）は、旧受付画面の項目をそのまま通常のフォームにした暫定のもの。

## 1. 前提にする場面（決定）

| 項目 | 前提 |
|---|---|
| いつ・どこで | 葬儀の後（当日の夜〜数日）に自宅で。当日の受付ではアプリを使わない |
| だれが | 喪主か家族が 1〜2 人で。手分けするときは同時に入力する |
| 手元にあるもの | 香典袋（表書き: 氏名・団体名・連名／中袋: 金額・住所）、芳名帳・芳名カード（氏名・住所・電話・関係）、現金 |
| 件数 | 家族葬 20〜30 件、一般葬 50〜150 件（ADR-P10） |
| 何のために | ① 誰からいくらいただいたかの記録 ② 現金の合計との照合 ③ 香典返し（住所が要る） |
| 金額の分布 | 3,000 円・5,000 円・10,000 円がほとんどで、親族は 30,000 円・50,000 円が多い |

## 2. 今の登録画面の課題

1. **入力欄が多い**。必須は 2 つ（氏名か団体名、香典なら金額）なのに、1 画面に 16 個の欄がある（行事・種別・氏名・金額・ふりがな・関係・団体名、「詳細」の中に 9 個）。どこまで入れればよいか迷う
2. **金額を毎回打つ**。「10000」の 0 の数え間違いが起きやすく、スマホでは数字キーへの切り替えも要る
3. **住所の入力が重い**。香典返しに必要なのに「詳細」の中にあり、郵便番号からの補完もないので全部手で打つ
4. **合計が見えない**。入力しながら件数と合計が分からないので、現金と合っているかを最後に一覧で確かめるしかない
5. **1 件ごとに画面を読み直す**（暫定のフォーム）。直前の登録を直すには別の画面へ移る
6. **種別ごとに要らない欄がある**。香典の入力中に品名・数量・弔電の文面の欄が並ぶ
7. **PC で 100 件をフォームで 1 件ずつ入れるのは遅い**。表に一気に入れたい

## 3. 目標

| 指標 | 今 | 目標 |
|---|---|---|
| 香典 1 件（氏名と金額）の操作 | 氏名 → 金額欄 → 数字 5 桁 → 登録 → 読み直し | スマホ: 氏名 → 金額のボタン → 登録。PC: 氏名 Tab 金額 Enter（読み直しなし） |
| 住所まで入れる場合 | 「詳細」を開き、郵便番号と住所をすべて打つ | 郵便番号 7 桁で町域まで入り、番地から先だけを打つ |
| 現金との照合 | 一覧で絞り込んで確かめる | 登録画面の上に、行事ごとの件数と香典の合計を常に出す |
| 間違えたとき | 一覧から詳細を開いて直す・削除する | 直前の登録の「取り消す」「直す」がその場でできる |

必須の項目は増やさない。キーボードだけで操作でき、axe の検査（WCAG 2.1 AA）を通すことは今と同じ。

## 4. 案

### 案 A: かんたん登録（項目を絞ったフォーム）

```
┌─────────────────────────────────────┐
│ 通夜 ▾            12 件・香典 ¥185,000 │  ← 行事と、その行事の合計（常に表示）
├─────────────────────────────────────┤
│ [香典] 供物  供花  弔電               │  ← 既定は香典。種別で出す欄を変える
│                                     │
│ 氏名  [                           ] │
│       ┌ 同じ人が登録されていませんか？┐ │  ← 候補（E5-1。今と同じ）
│ 金額  [         ] 円                 │
│       [3千] [5千] [1万] [3万] [5万]   │  ← 押すと金額欄に入る
│ 住所  〒[       ] → 町域まで自動で入る │
│       [                           ] │
│ ＋ ふりがな・関係・団体名・備考         │  ← 開くと出る
│                                     │
│ [        登録して次へ        ]       │
├─────────────────────────────────────┤
│ 登録した記録（この画面で登録した分）    │
│ No.12 佐藤 一郎   ¥10,000  [直す][取消]│
│ No.11 鈴木 花子    ¥5,000  [直す][取消]│
└─────────────────────────────────────┘
```

- 最初に出す欄は「氏名」「金額」「住所」だけにする。ふりがな・関係・団体名・役職・電話・備考は「＋」で開く（開いた状態は端末に覚えておく）
- 金額の欄の下に 3,000〜50,000 円のボタンを置く。押すと金額の欄に入る。キーボードではそのまま数字を打てばよい。「1万」「5千」「一万円」も受け付ける（`packages/domain` の金額の解釈を広げる）
- 種別は既定で香典。供物・供花は「品名・数量・金額（任意）」、弔電は「文面」と、種別ごとに必要な欄だけを出す
- 登録は htmx で部分更新し、画面を読み直さない。登録した記録を下に積み上げ、その場で「直す」「取り消す」ができる。すぐ戻せるので確認の画面は出さない
- 画面の上に、選んでいる行事の件数と香典の合計を出す。他の人が登録した分もリアルタイムに反映する（E8-1 の仕組み）
- 行事が 1 つだけのときは行事の選択欄を出さない。あわせて、香典帳を作るときの既定の行事を「通夜」「告別式」の 2 つから「葬儀」1 つにするかを決める（§6）

| 長所 | 短所・注意 |
|---|---|
| 効果の大きい課題 1〜6 をまとめて解ける。DO の `createGift`・`deleteGift` をそのまま使え、スキーマも変えない | 住所の補完には郵便番号のデータが要る（案 E） |

規模: 小〜中。

### 案 B: 一行入力（「佐藤一郎 1万」）

```
┌──────────────────────────────────────┐
│ [ 佐藤一郎 1万                      ] │
│   → 氏名: 佐藤一郎 ／ 香典 ¥10,000     │  ← 打ちながら、分けた結果を見せる
│ [ 登録 ]                              │
└──────────────────────────────────────┘
```

- 1 つの欄に「氏名 金額」を打つと、氏名と金額に分けて登録する。「1万」「10000」「１万円」「壱萬円」を読む
- スマホのキーボードの音声入力で「佐藤一郎さん、1万円」と話しても入る（アプリ側で音声認識は作らない）
- 案 A の氏名の欄にこの解釈を足す形にもできる（氏名の欄に金額まで書けば、金額の欄に移す）

| 長所 | 短所・注意 |
|---|---|
| いちばん速い。PC でもスマホでも欄が 1 つ | 団体名・連名・住所は入れにくい。読み違い（「三千」と「3000」など）があるので、分けた結果の表示が欠かせない |

規模: 小（解釈は純粋関数なのでテストしやすい）。

### 案 C: 表で入力（PC 向け）

```
┌────┬──────────┬──────────┬────────┬─────────┬────────────────────┬──────┐
│ No │ 氏名       │ ふりがな  │ 金額    │ 郵便番号  │ 住所                 │ 関係  │
├────┼──────────┼──────────┼────────┼─────────┼────────────────────┼──────┤
│ 11 │ 鈴木 花子  │ すずき…   │  5,000 │ 100-0001 │ 東京都千代田区千代田1-1 │ 友人  │
│ 12 │ 佐藤 一郎  │          │ 10,000 │          │                    │ 親族  │
│    │ ▌         │          │        │          │                    │      │ ← Enter で次の行
└────┴──────────┴──────────┴────────┴─────────┴────────────────────┴──────┘
```

- 表計算ソフトのように、Tab で右の欄、Enter で次の行へ移る。行ごとに自動で保存する
- 中袋を見ながら住所まで一気に入れる人向け。50〜150 件のときに効く
- Excel・Google スプレッドシートからの複数行の貼り付けで取り込む（紙から先に Excel に起こした人、葬儀社の芳名録のデータ）
- 差出人の一覧の行内編集（「保存して次へ」）の仕組みを広げて作る
- **決定（ADR-P19）**: 採る。表で入力するのは PC（画面幅 768px 以上）だけの動きにする。スマホのいただきもの一覧は 1 件 1 枚のカードで表示する（カードは実装済み。番号・差出人・種別・金額を出し、カードを押すと詳細へ移る）

| 長所 | 短所・注意 |
|---|---|
| 件数が多いときにいちばん速い。住所まで 1 回で入る | キーボード操作・読み上げ・同時編集の競合の扱いが難しい。クライアントの JS が増える（ADR-T02 の例外のアイランドを使うかの判断が要る） |

規模: 中〜大。

### 案 D: 写真から読み取る（香典袋の中袋・芳名カード）

- スマホで中袋や芳名カードを撮ると、氏名・金額・郵便番号・住所を読み取って下書きにする。確かめて「登録」を押す
- 手書きの住所を打つ手間がなくなるので、効果は最も大きい
- **決定（ADR-P19・ADR-T16）**: 採る。差出人の個人情報を AI に送ってよいが、学習には使わせない。送り先は、送ったデータを学習に使わないと規約で約束している API に限る（候補: Claude API、Workers AI）。読み取った結果は下書きにして、人が確かめてから登録する

| 長所 | 短所・注意 |
|---|---|
| 住所の入力がほぼ不要になる | 手書き・縦書き・旧字体の金額（「金壱萬円」）の読み取りの精度が分からない。1 枚ごとに費用がかかる。プライバシーポリシーに送り先と目的を書く必要がある |

規模: 大。送り先を決める前に、実際の香典袋 30 枚ほどで精度と費用を比べる。

### 案 E: 郵便番号から住所を入れる（案 A・C の補助）

- 郵便番号 7 桁を入れると、都道府県・市区町村・町域を住所の欄に入れる。番地から先だけを打てばよい
- 日本郵便の郵便番号データ（約 12 万行）を先頭 3 桁ごとの JSON にして Static Assets に置き、画面がそのファイルだけを読む（ADR-T17）。利用者の入力を外部の API に送らない。データはデプロイのたびに最新のものから作る
- 宛名の印刷（E7-2）の前に、住所から郵便番号を補う用途にも使える

規模: 小〜中（データの取り込みと更新の仕組み）。

### 検討したが採らない案

| 案 | 採らない理由 |
|---|---|
| 参列者が自分で入力する（受付に QR コードを置くデジタル芳名帳） | 家族の入力はなくなるが、当日の受付での運用になり ADR-P18 と合わない。ログインしない人の書き込みになり、いたずら・なりすましへの対策が要る |
| 金額ごとの件数だけを入れる（「5,000 円 × 12 件」） | 香典返しは人ごとに要るので、結局あとで 1 件ずつに分けることになる |

## 5. 進め方

| 段階 | 内容 | 状態 |
|---|---|---|
| 0 | 「受付番号」を「番号」にし、登録後に大きく出す。一覧を番号で探せるようにする。スマホの一覧をカードにする | 済み |
| 1 | **案 A + 案 E**（項目を絞ったフォーム、金額のボタン、行事ごとの合計、直前の登録の取り消し、郵便番号から住所） | 済み（案 E のデータはデプロイ時に作る。ADR-T17） |
| 2 | **案 C**（PC の表入力と貼り付け） | 次に作る |
| 3 | **案 D**（写真から読み取る）。送り先を実物の香典袋で比べて決め、プライバシーポリシーを直してから公開する | 採用済み |

案 B は段階 1 の後、利用者の声を見て案 A の氏名の欄に足すかを決める。

## 6. 決まったこと

| 項目 | 決定 | 記録 |
|---|---|---|
| 前提にする場面 | 葬儀の後に、家族が手元の香典袋を見ながら入力する | ADR-P18 |
| 番号 | 残して「番号」と呼ぶ。登録後に大きく出し、香典袋に書いて照合・管理に使う。一覧で番号を検索できる | ADR-P04 |
| 案 C（表で入力） | 採る。表の入力は PC だけ。スマホの一覧はカード | ADR-P19 |
| 案 D（写真から読み取る） | 採る。個人情報を AI に送ってよいが、学習には使わせない | ADR-T16 |
| 既定の行事 | 「葬儀」1 つ（通夜と告別式をまとめる） | ADR-P01 |

## 7. 残っていること

### 7.1 既定の行事と、行事の種類（決定）

香典帳を作るときに用意する行事は「葬儀」1 つにする（ADR-P01 の更新。実装済み）。今ある種類（`events.kind`）をそのまま使うので、DO のスキーマは変えない。旧アプリから移した香典帳は、すでに「葬儀」1 つになっている。これまでに作った香典帳（「通夜」「告別式」）はそのまま。

| 種類 | 値 | 既定の名前 | 使い方 |
|---|---|---|---|
| 葬儀・告別式 | `funeral` | 葬儀 | 香典帳を作ると 1 つ用意する。通夜と告別式の香典をまとめて入れる |
| 通夜 | `wake` | 通夜 | 通夜と告別式を分けて記録したい人が、設定で足す |
| 四十九日 | `memorial_49` | 四十九日 | 日付を入れると香典返しの期限の基準になり、期限の 14 日前と 3 日前にお知らせメールが届く（E6-5） |
| 一周忌 | `memorial_1y` | 一周忌 | |
| その他の法要 | `memorial_other` | その他の法要 | 別の日の初七日、初盆（新盆）、三回忌など。名前は自由に付けられる |
| その他 | `other` | その他 | お別れ会・偲ぶ会など |

変えたのは、既定の行事（`DEFAULT_EVENTS`）と「告別式」の表示名だけ。番号は行事ごとの連番なので、行事が 1 つなら香典帳全体の通し番号と同じになる。行事が 1 つなら登録画面で行事を選ばせない。

### 7.2 そのほか

| # | 項目 | 選択肢 | 推奨 |
|---|---|---|---|
| 1 | 写真をアプリに保存するか（案 D） | 保存しない（読み取りに使うだけ）／ R2 に保存して記録から見られるようにする | 保存しない。個人情報を持つ場所を増やさない |
| 2 | 写真の読み取りの送り先（案 D） | Claude API ／ Workers AI | 実物の香典袋で精度と費用を比べて決める |
| 3 | 今の暫定の登録画面 | 段階 1 を作るまで、このまま本番に出してよいか | 出してよい。項目は旧受付画面と同じで、登録のたびに画面を読み直すことだけが変わる |
